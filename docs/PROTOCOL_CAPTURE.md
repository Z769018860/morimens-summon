# 通讯数据自动获取：2026-10-01 实测结果

## 已确认的抽卡历史接口

本机被动抓包经 TCP 重组、Sconn 握手、DH/RC4、LZ4、sproto 和 MessagePack 解码后，恢复出真实 RPC：

- 方法：`Summon.QuerySummonHistory`
- 请求参数：`[historyType, page]`，页码从 1 开始，每页最多 5 条。
- 响应主体：`{"count": 总数, "records": [记录...]}`。零条时可能省略 `records`。
- 记录字段：`itemTid`（数值物品 ID）、`name`（`Item_<tid>_Name|中文名`）、`playerId`、`timestamp`（Unix 秒）、`type`（与请求类别一致）。

类别 2 与角色活动历史画面、类别 1 与命轮历史画面核对成功。角色前三页的 15 个时间点均吻合；名称有两处 OCR 将“谵妄”误读为“妄”，以通讯数据和原画面为准。类别 10、16、17 在抓包中也出现，暂只保留数值类别，不推断其含义。本次界面操作时观察到类别 2 总数 203、类别 1 总数 80、类别 10 总数 505、类别 16 总数 55、类别 17 总数 0；这些总数是当次账号快照，并非游戏常量。

历史 `itemTid` 与其他接口里的 `awaker.id` 不能直接等同。例如历史中“蚀灭·萝坦”为 145294，“潘狄娅”为 9674；旧研究资料中的对应觉醒体 ID 不同。实体映射应以历史响应的 `itemTid` 为主键。

## 采集与导出

`capture_passive_8443.py` 在游戏进程外通过 WinDivert SNIFF 被动记录 TCP 流。需管理员权限，并须在游戏连接建立前启动；本机加速器场景下还要观察本机端口 12887。原始 pcap、登录帧、截图和用户记录都只放在被 Git 忽略的 `data/local` 中。

`decode_summon_capture.py` 将完整抓包还原为请求与响应配对；`extract_history_records.py` 验证字段、去掉 `playerId`，输出结构化 JSON 与 CSV。曾从实际抓包中整理出 10 个唯一页面、45 条记录。它们尚不构成完整历史。

`fetch_all_history.py` 是只读独立 RPC 查询实验：从当前游戏进程或本次抓包取得授权材料，仅驻留内存；复用已验证的登录结构，再逐页请求自己的历史。实测取得角色类别前 10 页共 50 条并保存断点。连续查询在第 17 页附近被服务器断开；第二次连接在登录阶段也被关闭。因此该脚本尚不能当作可靠的完整同步功能，运行时可能影响现有游戏连接。

## 已知限制与下一步

1. 解决独立查询的连接生命周期与限流问题，在小批量和断点续取下完成全部页；避免影响正在运行的游戏。
2. 验证尾页、空类别、不同类别的分页以及重复抓取一致性。
3. 明确类别 10/16/17 对应的界面历史，补齐稀有度和卡池规则的独立来源。
4. 将已验证的通讯记录接入本地分析数据库，并显示采集覆盖范围。所有保底分析都需要明确对应池规则与完整性。

Frida 进程内附加曾使游戏退出，故当前不再使用该路径。画面截图只用作明文锚点校验，不作为抽卡数据源。
