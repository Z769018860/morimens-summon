# 抽卡分析工具开发方案

更新日期：2026-10-01

## 目标与首版边界

首版让玩家把自己已知的抽卡记录导入本地，在角色、命轮和卡池维度查看次数、稀有度分布、保底进度及时间线。导入后可编辑和删除误识别记录。所有结果标示数据来源、覆盖范围和计算依据。

首版不依赖尚未恢复的 History RPC，也不提供“输入 UID 获取他人记录”的功能。自动采集是后续能力，只有真实响应明文和字段结构得到验证后才接入。

## 已有证据与实现影响

| 已知进展 | 实现影响 |
| --- | --- |
| 五页 25 条截图与响应已绑定 | 可做导入及人工核对的固定验收样本；不能把包长当作记录内容。 |
| `type2RecordQueue` 与保底状态字段存在 | 建立独立的历史记录与状态快照模型；不要推断静态空队列包含当前账号完整历史。 |
| `rewardList.tid/num` 已确认，`9741` 与命轮 ID 交叉验证 | 实体映射以数值 ID 为主、名称为展示字段；未验证的唤醒体 tid 单独标记。 |
| Session DH/RC4 等通用传输已知 | 协议层可单独研究；不能用抓包密文直接导入记录。 |
| History 方法、参数、普通记录 schema 未知 | 自动同步需要验证门槛，不排进首版交付。 |

## 分阶段实施

### M0：数据契约与测试材料

- 定义 `PullRecord`：本地记录 ID、卡池类别、卡池配置 ID（可空）、时间（可空）、实体 tid（可空）、显示名称、稀有度（可空）、批次 ID（可空）、来源、证据等级、原始来源定位。
- 定义 `SummonStateSnapshot`：各类保底计数、累计次数、快照时间与来源。记录和快照不混为同一种数据。
- 整理五页截图的去标识化测试样本及实体映射，保留无法确认的 ID 为空；维护来源和版本。
- 验收：25 条样本能导入、导出、去重、校对；导出再导入后内容不变。

### M1：可用的本地分析器

- 支持手动录入、CSV/JSON 导入和导出；为截图转录留出可选入口，但每条自动识别结果必须可人工确认。
- 按角色/命轮/池统计总抽数、SSR/SR 数、间隔、最近一次记录及时间线；筛选、纠错、重复检测。
- 保底进度只在池规则、计数起点和完整记录范围可确认时展示确定值；否则显示“依据不足”和已知区间。
- 验收：用固定样本核对计数、排序、去重、跨池隔离与不完整样本提示。

### M2：实体与卡池资料

- 引入带版本与来源的 `tid → 名称/类别/稀有度` 映射，优先复用已交叉验证的结构化 ID；补齐熟成/P14、洞悉/P16。
- 分开记录卡池配置 ID、卡池组 ID、历史类别；暂不把 `openDate/closeDate` 键或 `finishPool` 值直接认作历史请求参数。
- 验收：未知 tid 不阻止导入，映射更新不改写原始记录，名称冲突可追溯。

### M3：可选的自动导入研究

- 只接受真实授权账号的应用层明文导出，或完整验证的 post-login 解码链。
- 先确认 History RPC 方法、请求参数、响应字段、分页和缓存行为，再写只读适配器；用五页样本逐条对齐 UI、时间、tid、池类别。
- 凭据与会话材料只驻留在需要它们的运行期；默认不落盘、不进入日志。发现服务端字段变化时停止自动导入并提示核对。
- 验收：至少多会话、多池、多页重复验证；首尾页、空页、缓存返回与异步推送均可区分。

## 建议技术结构

采用本地优先的 Web 界面：TypeScript 前端、纯函数统计核心、浏览器本地存储。将数据导入、实体映射、统计规则和后续协议适配器分成独立模块。首版无需服务器或账号体系。具体框架在 M0 建立最小原型时确定，避免在数据语义未定前锁定技术栈。

## 下一步任务顺序

1. 完成 M0 数据契约与五页样本，明确每个字段的证据等级。
2. 制作 M1 的手动录入、导入导出和基础统计原型。
3. 整理实体映射及卡池规则来源，再开放保底分析。
4. 按 M3 门槛继续协议研究；只有解出真实 History 明文才承诺自动同步。

## 公开仓库检查

在公开任何研究材料前，检查账号标识、票据、Cookie、Token、会话密钥、抓包、截图中的个人信息，以及第三方数据和游戏资源的再分发范围。默认仅提交自写代码、文档与去标识化样本。
